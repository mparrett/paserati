Background — two tracks

Sequel to a TinyGo wasi hello-world: the next step was a heavy real binary to stress paserati's wasm→bytecode transpiler. let-go was the ideal target — but it didn't build for wasi. That split the work in two independent, synergistic tracks.

Track A

Should let-go support a wasip1 build — and is a wazero-embeddable, sandboxed let-go worth pitching upstream to nooga? (let-go side)

Track B

What does the transpiler hit on a heavy real binary, and which gaps are worth closing? Once let-go builds for wasi, it is the stress target. (paserati side)

The two walls

The asyncify gowrapper — TinyGo's goroutine trampoline — tripped both structural limits of paserati's bytecode. Removing goroutines and sweeping -opt shrinks them, but no single knob clears both: they trade.

04

Findings

let-go side

  • wasi is a 3-line gate, not a port. Extend the !js platform gates to !wasip1 (readline REPL + term). Stock Go and TinyGo fail identically pre-fix.
  • The 64-bit-int wall is TinyGo-specific, not wasi-specific. Stock-Go wasip1 is numerically faithful; TinyGo's int is 32-bit. Toolchain choice is a size-vs-fidelity knob.
  • runtime_only is a bounded packaging change — ~90% latent in the tree. It's the trust/embedding surface for the wazero pitch.
  • Goroutine-free is the right wasi shape. On the wasm MVP, asyncify is the only goroutine mechanism and it is the gowrapper — cooperative concurrency, never parallelism. Removing it is a bounded, feature-scoping fork.
  • The residual fat function is eval/apply-shaped, inherent to TinyGo's lowering. Asyncify made it monstrous; without it, merely large.

paserati side

  • Two structural limits in the bytecode: byte-indexed registers (≤256) and int16 jump offsets (±32 KB). The gowrapper tripped both — 560 locals, ~557 KB jumps.
  • Register widening was never needed — the spiller covers it. Over-256 functions park all locals in an array at R0; normal functions keep the fast direct-register path. Transpiler-only, no VM change.
  • The jump wall closed additively. OpJumpLong/OpJumpIfFalseLong + a monotonic branch-relaxation fixpoint. Stock TS compiler never emits them, so existing bytecode is unchanged.
  • Latent bug fixed, un-masked by un-stubbing. The direct→spilled retry reused stale constant-dedup caches; Chunk.Reset() now clears them. Not a jump bug — it crashed on instruction two.
  • i64 runs on exact-BigInt helpers — correct for full 64-bit fidelity, no VM change. It allocates, so native i64 is a perf lever, not a correctness gate.
Joint result

All four builds (asyncify + nogoroutine × opt2 + optz) run byte-identical to wasmtime, zero int64/VM fork. The residue — a few long jumps, one fat function — lives entirely in paserati's additive machinery. Nothing in let-go's value model or eval core changed; stock TS bytecode is untouched.

Next steps

All orthogonal, all perf / outreach — not correctness. Correctness is done.

let-go side

  1. Productionize goroutine-free behind a nogoroutine build tag so native/browser keep real goroutines. Open Q: can xsofy itself ship on it, or is it transpiler-target-only?
  2. Track A — the wazero embedding pitch to upstream (nooga). Gating is proven; the deciding factor is a concrete embedding consumer.
  3. Outbound draft cleanups (held for human review): tinygo-support int-width precision, runtime-only status, stack-overflow framing.

paserati side — none urgent

  1. Bytecode self-check pass. A verifier for jump targets on instruction boundaries and in-range constants — would have caught the resetChunk bug at compile time.
  2. Smarter spilling. Spilling only the overflow (not all locals) cuts code size and jump pressure — the one lever that shrinks both walls at once.
  3. Upstream the long-jump opcodes. Additive and self-contained — a clean candidate independent of the transpiler.
  4. Native i64 in the VM. Cuts BigInt allocation. Pure perf, only if profiling shows it dominates.
